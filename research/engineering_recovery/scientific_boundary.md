# Engineering Recovery Scientific Boundary

This recovery starts from commit `32a8333bf0106579834fb7a0747c81d67b49ac10`, where
no formal Atomic or Joint model forward had occurred. The historical
`BLOCKED_BY_MODEL_ADAPTER` report remains an immutable record. Its
`NO_FEASIBLE_COHORT` wording is not a model-capability conclusion because there were no
formal task outputs.

The work is limited to dependency completeness, isolated Python environments, native
model/processor interfaces, image preprocessing, memory placement, quantization mechanics,
candidate microbatching, engineering-only smoke execution, and engineering reporting. It is
not a new model experiment, checkpoint replacement, prompt tuning, result rescue, scientific
amendment, or capability evidence.

The three model families, model IDs, exact model/processor/tokenizer revisions, formal data,
prompts, demonstrations, candidate answers, answer contracts, thresholds, model-selection
policy, statistical methods, and scientific estimands remain frozen. No fourth model may be
added, and no checkpoint may be selected from task performance.

Engineering-only scenes may establish only that a real image reached the vision path, a
forward completed, all frozen candidates received finite conditional log-likelihood scores,
constrained generation stayed within the allowed set, deterministic reruns agreed, and the
artifact is recoverable. Their task accuracy must not be reported or used to alter a prompt,
visual budget, model, or checkpoint.

Atomic qualification is unauthorized until at least two independent frozen families pass the
engineering gate. Joint composition is unauthorized until at least two families are
`ATOMICALLY_QUALIFIED`. Activation patching is forbidden throughout this recovery.

Failure to fit a frozen 7B--10B model on the local 6 GiB GPU is a compute boundary, not a
scientific model failure. A compute migration must retain the same model, revision, data,
prompts, candidates, thresholds, and answer contracts.
